The document specifies FOUR items (full extracted Bulgarian text at the bottom of this

### B1. „Складови операции" — Warehouse Operations report (→ Reports app)
Purchases & sales of goods for a period. Filters (combinable): period from/to; operation
(purchases | sales); warehouse; document type; product; **product group** (category);
contact (customer for sales, supplier for purchases). „Изведи" (Generate) button → rows
traceable per article with quantities, prices, values. **Column settings after generation**
(show/hide/reorder) without regenerating — reuse `useGridColumns`/`GridColumnPickerDialog`
(FR-05 DnD) and `useListQueryState` for the filters.
Codebase anchors: the data is essentially the product-ledger aggregation across products —
`packages/services/src/biz/product-ledger.service.ts` (per-product), movements list
(`warehouse-api/src/controllers/movement.controller.ts`), and invoice lines. Likely a new
aggregation endpoint (e.g. `/org/:orgId/reports/warehouse-operations`); export via the
`packages/reporting` XLSX/PDF house style (see `cash-agg.excel.ts`/`cash-agg.pdf.ts` for
the freshest pattern incl. per-currency sections and totals row).

### B2. „История на продажбите" — Sales History / cash reconciliation report (→ Reports app)
All register-related sales for a period: sales invoices paid **in cash**, sales invoices
paid **by card** (clearly distinguished), and **cash sales**. Columns: date, **time**,
register, user, operation/sale number, contact (when present), status, invoice number
(when issued), value, payment method (cash/card). End summary: system sales ↔ expected
cash ↔ card payments, for end-of-day comparison.
Anchors: `Invoice` docs (`type: 'invoice'|'cash_sale'`, `payments[].method`,
`paymentMethod`, `buildPaymentMethodFilter` in `invoice.controller.ts`) + `POSTransaction`
(`pos.controller.ts` `GET /transactions`) — decide whether POS transactions are included
(they are a separate collection from cash-sale invoices!) and say so explicitly in the FR.
„Register"/„user" map to POS session / `createdBy`.

### B3. „Каса и приключване" — Cash-register end-of-day close (function, NOT a report —
decide placement: POS app or a card in Reports; flag the choice to goran in the FR)
Operator enters the **actually counted** amounts (cash, card, other configured methods);
system shows the **expected** amounts from the ledger; visual comparison; on „Приключване"
run the **fiscal day-close (Z-report) on the fiscal device** and print it; afterwards show
success / failure / **communication-error** state — on error the day must NOT be marked
closed, with a clear message.
Anchors: POS session close already exists (`pos.controller.ts:275`
`POST /session/:id/close` — computes expectedBalance/difference; `pos.session.closed`
event → batch dispatch + JE in `services/src/events/handlers.ts:175`). Z-report exists at
`portal-api/src/controllers/fiscal-device.controller.ts:184` (`POST /:id/z-report`).
The FR is largely about WIRING these together + the counted-amounts entry UI + the
error-state contract (fiscal bridge via `useFiscalBridge`, browser Web Serial). Mind
SUPTO_MODE=production semantics.

### B4. „Изпращане на изходящи фактури по имейл" — Email an outgoing invoice (→ invoicing)
A „Send by email" action on sales invoices: takes the invoice, prepares it (PDF — reuse
`GET /invoicing/export/:id?format=pdf`, `invoice.pdf.ts`), lets the user enter/select the
recipient (prefill from the contact card `email`, editable), sends it **as an attachment**,
clear success/failure message.
Anchors: `packages/services/src/biz/email.service.ts` — SendGrid via
`config.email.sendgridApiKey`, logs to `EmailLog` (`db/models/email-log.model.ts`) —
BUT it currently supports HTML body only, **no attachments**, and silently no-ops when
the API key is missing: the FR must extend it (SendGrid `attachments[]`, base64) and
define behavior when unconfigured (explicit error to the user, not a silent skip). Check
whether prod has SENDGRID_API_KEY set before promising delivery in the field test.
Also specify: EmailLog entry per send, audit entry, and (SHOULD) a "sent to X at Y"
indicator on the invoice.

### Every touchpoint for adding an app (collected so nothing is missed)

1. `packages/config/src/constants.ts:72` — `APP_REGISTRY` entry
   (`reports: { name: 'Reports', icon: 'mdi-file-chart', color: …, devPort: 4101,
   path: '/reports/', requiredPermission: 'invoicing.read', description: … }`) + the
   `AppId` union it is keyed by. ⚠ **`PLAN_APP_LIMITS` is right below (`free: 5,
   starter: 5`)** — with a 6th app the free/starter plans will hide one app; raise the
   limits or confirm regal's plan covers it, and note the decision in the FR.
   Pick `requiredPermission` deliberately: `invoicing.read` matches the moved reports and
   keeps `nra_auditor` able to read/export (see `lib/export-access.ts` rationale).
2. **New package `packages/reports-ui/`** — clone the smallest existing UI package's
   scaffold (`pos-ui` is the leanest: vite config, `?token`/`?org` handoff in
   `router/index.ts`, app.store, DefaultLayout). Use `AppShell` WITHOUT the `menu-bar`
   slot (no top menus); home view = card grid modeled on
   `packages/portal-ui/src/views/AppHubView.vue` and the `AppSwitcher` tile styling.
   Include `scrollBehavior` (FR-05 convention) and `useListQueryState` on any grid.
3. `packages/portal-api/src/unified.ts` — serve the built UI at `/reports/` + SPA
   fallback (mirror how the other 6 UIs are mounted); root `package.json` —
   `dev:reports-ui` script and add the build to `bun run build`.
4. `packages/ui-shared/src/nav/page-registry.ts` — `APP_NAV_META.reports =
   { base: '/reports', devPort: 4101, nameKey: 'apps.reports' }` + `page()` rows for each
   report card (★ favorites keep working).
5. i18n ×4: `apps.reports` + `apps.reportsDesc`; move/keep `nav.agingReport`,
   `reporting.export.*` keys (they live in ui-shared, shared across apps — no move needed).
6. **Org enablement**: the App Hub reads `GET /org/:id/apps` backed by `OrgApp` docs —
   check how a new app becomes enabled for existing orgs (seed/settings/admin toggle) and
   spec it; otherwise the card won't show for regal. (`docs/models/core/org-app.md`.)
7. **Invoicing cleanup + redirects**: remove the two pages from invoicing's router/nav
   (`invoicing-ui/src/layouts/DefaultLayout.vue` Reporting group — decide whether the
   group survives with cross-app links or disappears; FR-01 removed groups before, users
   adapted). Keep old paths as redirects. ⚠ Cross-app redirect: invoicing and reports are
   separate SPAs — a Vue-Router redirect can't cross apps; use a tiny route component that
   does `window.location.href = '/reports/…'` (or the `navigateToPage` helper in
   `ui-shared/src/nav/navigate.ts`, which handles dev-port + token handoff in local dev).
8. **Docker/deploy**: confirm the Dockerfile builds UI packages by glob or list — if it
   enumerates them, add `reports-ui`; the deploy-prod skill needs no change. The nginx-less
   unified server serves whatever `bun run build` produced.
9. e2e: a smoke spec that the hub renders cards and each card opens; the moved pages keep
   their specs with updated URLs (grep `aging-report|reporting/export` under
   `packages/e2e/`).
